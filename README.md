# NASA ULI Flight Data

Flight test data from the NASA University Leadership Initiative data collection, with wind data recorded
alongside the flights.

**Website:** https://afnasa-uli.github.io/flightdata/. It has experiments by drone and date with
interactive plots, raw-data browsing, and downloads (everything, all processed data, or per drone).

## Layout

```
raw_data/<flight>/             flight logs exactly as offloaded; never edited
raw_data/wind_drone/           wind-drone ROS 2 bags (+ _csv exports); matched to flights by time
raw_data/hwas_data/            USAFA mesonet HWAS weather-station exports (30 s); matched to flights by time
processed/<flight>/            generated by the pipeline; don't edit by hand
    flight.parquet, flight.csv   cleaned flight data, standard columns
    wind.parquet, wind.csv       wind data for this flight's time window (when a wind log overlaps)
    hwas.parquet, hwas.csv       HWAS weather-station readings from 1 min before to 1 min after the flight
    metadata.json                header, summary, data-quality checks, column units, provenance
nasauli/                       the processing pipeline and website generator (Python)
book/                          hand-written website pages and Jupyter Book config
notebooks/explore_flight.ipynb load and plot a processed flight (also runs in Colab)
.github/workflows/build.yml    on push to main: process data, commit processed/, publish the website
```

## Adding a flight

1. Put the logger CSV in a new folder `raw_data/<Drone>_<YYYYMMDD_HHMMSS>Z/` (don't open and re-save it in
   Excel), and any new wind-drone bag plus its `_csv` export in `raw_data/wind_drone/`.
2. Push to `main`. The GitHub Action processes the data, commits `processed/`, and republishes the website.

A new drone needs one entry in `nasauli/platforms.py`.

## Running locally

```bash
pip install -r requirements.txt                 # processing
python -m nasauli process                       # raw_data/ -> processed/
pip install -r requirements-site.txt            # website
python -m nasauli site --out _site              # open _site/index.html
```

## Cleaned data

`processed/<flight>/flight.parquet` (or `.csv`) holds one row per logger sample. The first columns are a
**standard schema** with fixed names and units (`time_utc`, `time_gps_utc`, `alt_rel_m`, `roll_deg`,
`batt_voltage_v`, `north_m`, …); the full list is in `nasauli/schema.py` and on the website's *Processed data*
page. The remaining raw logger columns follow under their original names.

- `armed` uses only the autopilot's heartbeats; the raw `HB_Armed` column also contains other MAVLink
  components' heartbeats.
- `time_gps_utc` is the logger clock corrected to the autopilot's GPS time. Wind data is matched on it.
  `time_local` is the same instant in Mountain Time (MST/MDT); the website shows Mountain Time throughout.
- Wind: the sensor's `vector.x` is speed (m/s) and `vector.y` is direction (deg, where the wind comes from).
  HWAS timestamps are Mountain Time; it reports whole knots and °F (exported as SI), and its pressure is
  sea-level-adjusted. The autopilot's `WND_*` wind estimate (`ap_wind_*`) is not a measurement and is not used.
- Accuracy: RTK positions are centimeter-level *relative to the base station* (an Emlid Reach RS2+ that was not
  on a surveyed point, so absolute coordinates can be off by a few meters). `alt_rel_m` is barometer-based and
  drifts ~1–2.5 m from the RTK height; use `gps_alt_m` during RTK Fixed for precise height. Details are on the
  website's *Processed data* page.

## Log formats

Each log format has a reader in `nasauli/readers/` that converts it to the standard schema:
`session_v2` (`# nasauli session log v2.x`) and `legacy_v1` (the April 2026 logger). When the logger format
changes, add a reader and keep the old ones. Every output records the pipeline version and reader used.
